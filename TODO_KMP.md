# Quran & Sunnah — Kotlin Multiplatform + Native UI Migration

Goal: rebuild as KMP shared logic + native UI (Android Jetpack Compose,
iOS SwiftUI), reach full parity with the Flutter app, then delete Flutter.

Non-negotiables carried over: verified-only sacred text (never synthesize
Ayah/Hadith), offline-first, trilingual UI (ar/en/fr), data licenses intact
(`docs/DATA_LICENSES.md`, `assets/licenses/DATA_NOTICES.txt`), same
applicationId (`com.godfather59.quransunnah`) and release keystore for store
continuity. Target UI stack: Jetpack Compose (M3) + SwiftUI. Shared code in
Kotlin (`shared/` module); platform code only for UI, audio output,
notifications delivery, GPS, and file I/O.

Strategy: build shared module first (pure Kotlin, fully unit-tested), then
native UIs against it, then cut over. No Flutter edits except critical fixes
during migration.

Fresh install only — no legacy SharedPreferences import. 12 tests ✅ (incl. backup round-trip, invalid backups keep data, garbage rows skipped).
- [x] Port prefs: multiplatform-settings 1.3.0 `Prefs` wrapper with exact key names (`q.*`, `app.*`, `prayer.*`, `home.*`, `khatma.*`, `memorized.*`, `dhikr.*`, `search.history` max-10). Lists stored unit-separator-encoded. 8 tests ✅.
- [x] Search index: FTS5 MATCH + bm25 query (parity with Dart customSelect), fingerprint-gated rebuild helper, 6236-row round-trip ✅. 5 tests.
- Notes: sqlite_3_18 codegen dialect can't parse upserts — in-place update-then-insert pairs used instead (same observable semantics, preserves highlight order). multiplatform-settings has no generic `get` inference — explicit getters used; tests use `MapSettings`. iOS clock/driver are deliberate compile-time stubs for Phase 6 (macOS-only APIs). Startup-crash fix (logcat: `no such module: fts5` inside `Schema.create` on the Home screen's first frame): that Xiaomi's SQLite ships without the FTS5 module entirely, so schema creation threw on every open and every query retried it forever. `search_fts` + triggers + MATCH queries moved out of codegen into raw SQL — the library schema keeps all plain tables with `IF NOT EXISTS` and never touches FTS, so a missing module is simply unused. Raw `driver.executeQuery` mappers run once per call: row iteration via `cursor.next()` is the caller's job (mirroring generated `executeAsList`). JVM suite (whose SQLite bundles FTS5) still covers the full FTS round-trip.
